## Chapter 2: Dependency Management (Bzlmod)
The Bazel module system (Bzlmod) is the modern, recommended way to handle external dependencies in Bazel projects, replacing the older, complex `WORKSPACE` file mechanism. Bzlmod ensures dependency resolution is deterministic, transitive, and easier to manage at scale.

## 2.1 Introduction to Bzlmod and the Bazel Central Registry (BCR)
- Bzlmod (Bazel Module): Every Bazel project is considered a module. Modules depend on each other by specifying `bazel_dep` in their `MODULE.bazel` file.
- The Bazel Central Registry (BCR): This is a decentralized repository hosted on GitHub (`bazel-registry/bazel-central-registry`). It serves as the primary source for finding and fetching external Bazel modules and rules (like `rules_cc`, `rules_go`, `rules_python`).
- Module Identity: Your project's `MODULE.bazel` file must declare its identity:

```
# MODULE.bazel
module(
    name = "my_bazel_project", # Unique name for your module
    version = "0.1.0",         # Current version of your module
)
```
## 2.2 Declaring External Dependencies
To pull in external tools or rule sets (e.g., rules for Python, or GoogleTest for C++), you use the `bazel_dep` function inside your `MODULE.bazel` file.

### Using `bazel_dep`
`bazel_dep` declares a dependency on another Bazel module found in the BCR.

```
# MODULE.bazel

# 1. Dependency on a ruleset (e.g., rules_python)
bazel_dep(name = "rules_python", version = "0.33.0") 

# 2. Dependency on a C++ testing framework (e.g., googletest)
bazel_dep(name = "googletest", version = "1.14.0") 

# Dependencies are always resolved transitively and automatically.
```
### Versioning and Overrides
In large projects, you often need to control dependency versions or point to custom local or remote sources. This is done via Overrides.

| Override Type | Use Case | Example (in MODULE.bazel) |
|---------------|----------|---------------------------|
| `git_override` | To depend on an unreleased version, a specific commit,  or a fork that isn't yet in the BCR. | `starlark git_override( module_name = ""rules_python"",  remote = ""https://github.com/bazel-contrib/rules_python"", commit = ""a1b2c3d4e5f67890..."" )` |
| `local_path_override` | For local development or debugging dependencies that are not yet pushed to a remote repository. | `starlark local_path_override( module_name = ""my_internal_library"", path = ""../shared/internal_lib"" )` |

Note: Overrides must be placed after the module() call but before the corresponding bazel_dep calls in the MODULE.bazel file.

## 2.3 Lockfiles: Understanding `MODULE.bazel.lock`
Bzlmod resolves the transitive closure of all dependencies based on the MODULE.bazel file. To ensure reproducible builds and fast analysis after the first run, Bazel generates a lockfile.
- What is it? `MODULE.bazel.lock` is an automatically generated JSON file that pins the exact version, registry, and hash of every single transitive dependency used in your project.
- Why commit it? It must be committed to your version control system (Git) alongside your `MODULE.bazel` file. This guarantees that `bazel fetch` (or any build) will always use the exact set of dependencies defined in the lockfile, bypassing network resolution if the lockfile is up-to-date.
- Updating the lockfile: If you change a version in `MODULE.bazel`, Bazel will automatically detect the change and prompt you to run a command (e.g., `bazel mod tidy`) to update the lockfile.

## 2.4 Vendor Mode: Vendoring Dependencies for Offline Builds
While Bzlmod is designed to fetch dependencies on demand, some organizations require fully offline or air-gapped builds (where no network access is permitted). Bzlmod supports a vendor mode for this purpose.
- Purpose: To download all necessary external modules and save them locally in a controlled directory before the build starts.
- Process Overview:
    1. Resolve and fetch all dependencies using the standard Bzlmod process.
    2. Use a Bazel command to copy these fetched artifacts into a dedicated local vendor directory within your repository.
    3. Configure Bazel to only look in this local vendor directory, ensuring the build is entirely self-contained and network-free.
