# 1. Foundations & Environment Setup
The goal of this chapter is to set up a stable, hybrid Bazel environment using the recommended launcher, define our target version, and cover the essential architectural concepts required for the polyglot project.

## 1.1 Bazelisk Installation & Version Pinning
We'll start by ensuring we're using the correct version of Bazel, 7.7.1 LTS, via Bazelisk. Bazelisk acts as a wrapper that automatically downloads and executes the specified Bazel binary, ensuring your builds are always reproducible regardless of the machine.

| Step | Action | Description |
|------|--------|-------------|
| Install Bazelisk | Follow the official instructions for your OS (e.g., using Homebrew, Chocolatey, or downloading the binary). | Ensure the `bazel` command points to the Bazelisk executable. | 
| Pin the Version | Create a file named `.bazelversion` in the root of your project: `echo "7.7.1" > .bazelversion` | This tells Bazelisk which specific Bazel binary to use. | 
| Verification | Run: `bazel version` | The first time, Bazelisk will download the specified 7.7.1 binary. Subsequent runs will use the cached binary. |

## 1.2 The Hybrid Configuration (WORKSPACE & MODULE.bazel)
For complex polyglot projects, especially those involving older external rules like gRPC C++, the Hybrid Model is the most stable approach in the Bazel 7.x era.
- `MODULE.bazel` (The Future): This file is mandatory and used primarily for Bzlmod dependency management (rules like `rules_go`, `rules_python`). It defines direct dependencies using `bazel_dep`.
	```
	# MODULE.bazel
	module(
		name = "polyglot_project",
		version = "0.0.1",
	)
	# Future dependencies will be listed here.
	```
- `WORKSPACE` (The Bridge): This file is used to load legacy dependencies that rely on older loading mechanisms, like `http_archive` (which we will use later to manually override picky dependencies like Protobuf/gRPC C++).
	```
	# WORKSPACE
	# This file remains mostly empty for now, but its presence enables legacy dependency loading.
	# Future legacy dependencies (like gRPC C++ toolchains) will be defined here.
	```
- `.bazelrc` (Configuration Flags): Used for project-wide defaults, such as enabling Bzlmod and defining common configuration flags.
	```bash
	# .bazelrc
	# Enable Bzlmod by default (optional in Bazel 7, mandatory in Bazel 8)
	# build --enable_bzlmod
	# Common flags for C++/Python/Go development
	build --repo_env=CC
	build --repo_env=BAZEL_GO_SDK
	```
## 1.3 Core Concepts: The Bazel Architecture
### The Action Graph
Bazel operates on a Directed Acyclic Graph (DAG) of Actions.
The build process is structured around three elements:

| Element | Description | Example |
|---------|-------------|---------|
| Input | The source files and declared dependencies required for an action. | `hello.cc`, `greeter.proto`, `//external:protobuf` |
| Action | A command (like compile, link, or run) that Bazel executes hermetically. | `g++ -c hello.cc -o hello.o, protoc` generation. |
| Output | The resulting artifacts (object files, binaries, documentation, etc.). | `hello.o`, `server_cpp`, `generated .pb.h` files. |

### Labels, Targets, and Packages
These terms define how we reference code and rules within the Bazel workspace.
- Package: A directory containing a `BUILD.bazel` file. Packages form the logical structure of your project.
	- Example: `src/server_cpp` is a package.
- Target: An individual rule instance defined within a `BUILD.bazel` file. Targets are the fundamental units Bazel builds or tests.
	- Example: `cc_binary(name = "server")` defines the `server` target.
- Label: The fully qualified name used to reference a target from anywhere in the workspace.
	- Format: `//package/path:target_name`
	 -Example: `//src/server_cpp:server` (refers to the `server` target in the `src/server_cpp` package).
	 -External Labels: Start with `@@` (Bzlmod) or `@` (Legacy) and reference targets defined outside your project (in `MODULE.bazel` or `WORKSPACE`).
		- Example: `@@rules_go//go:def.bzl` or `@com_github_grpc_grpc//:grpc++`.
